# Engagement notes

_[← Project README](../../README.md) · [EA home](../ea/README.md)_

What the method did not tell us to do, and what we did instead. One note per
completed initiative or client engagement, numbered chronologically, written
with the `engagement-retrospective` skill.

These are `DOBJ7` — the mechanism behind `CAP10`, and the first stage of
[`COA1`](../decisions/1_take-coa1-staged.md).

## Why this exists

`CAP9` claims that the expertise sits in the method. `BSVC3` — consulting —
needs a person anyway. The difference between those two is knowledge that
lives in one head, and this folder is where it stops doing that.

Every method improvement in this repository so far started as somebody
improvising mid-work and noticing afterwards. That noticing used to be
accidental. Here it is a step.

## The three rules

**No client facts.** Names, figures, industries specific enough to identify —
none of it. A note records the **pattern**, never the case. The raw material
stays as `DOBJ4`, confidential, outside this repository. This folder is the
one place in the model where something crosses from confidential to public,
and it crosses in one direction only.

**A note that proposes nothing is still a note.** Not every engagement
teaches something. "Nothing generalizable this time" is a complete answer and
a useful one — it is how anyone tells whether the method is converging or
whether this mechanism is manufacturing lessons to justify itself.

**Proposals become initiatives, not edits.** A note never changes a skill. It
proposes, and each proposal goes through `ea-first-change` with the gates
that implies. A pattern that appears in **two** notes should be raised that
week; a pattern in one should wait, because the generalization test is
unreliable on a single case.
