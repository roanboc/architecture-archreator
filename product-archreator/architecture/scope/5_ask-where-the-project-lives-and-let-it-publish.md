# Project Scope — Ask where the project lives, and let it publish

_[← Scope index](./README.md) · [Model home](../README.md)_

**ArchiMate viewpoint:** Implementation & Migration.
**Delivered as:** the `claude/repo-agnostic-deployments-3e9qfb` branch in
[`archreator`](https://github.com/roanboc/archreator) — **not yet written**,
and the model changes this document holds the gate for.

The scaffold ships two validators that no project runs, and a portal that no
project hosts. Both gaps have the same cause: **the method never asks where
the project lives.** Unable to name a host, it emits nothing host-shaped and
settles for prose — [`docs/publishing.md`](https://github.com/roanboc/archreator/blob/main/docs/publishing.md)
carries a publishing workflow as a fenced code block that every adopter
retypes by hand, and the checks have no counterpart at all.

This initiative asks once, at bootstrap, and lets the answer activate what it
allows. A project on a public GitHub repository gets its checks running and
its portal published on the first push. Every other project gets exactly what
it gets today — a folder of static HTML and no opinion about where it goes.

## The two gaps, and why the second is the larger one

**A downstream project inherits `check_links.py` and `check_model.py` and
nothing that runs them.** `TSVC2`'s own recorded rationale is that "the
validators are worthless if running them is somebody's discipline" — a
statement this repository acts on for itself and has never extended to the
projects it emits. Every adopter inherits precisely the discipline problem
`TSVC2` was written to reject.

Publishing is the gap that was noticed; the checks are the gap that was not.
The checks are also the cheaper half: they need no repository setting enabled,
they are identical whether the repository is public or private, and they
cannot turn red on a project whose model is valid.

## What the answer decides

One question at bootstrap, and it is not a question about visibility alone:

| The answer | What is activated |
| ---------- | ----------------- |
| **A public GitHub repository** | The checks workflow, and the publishing workflow. The portal is world-readable, so the disclosure call is the Requester's, recorded here |
| **Any other GitHub repository** | The checks workflow only. On the free plan a private repository cannot publish Pages at all, so there is no second variant to design — the absence *is* the behavior |
| **Anything else** — Azure DevOps, GitLab, a private forge, undecided | Nothing. `build_docs.py` writes a folder and stops, exactly as today |

**Private is not a variant; it is the default.** That is what keeps this
initiative small: the method gains one branch, not a matrix, and the branch it
gains is the one where the platform can actually deliver.

The same answer settles three more things the scaffold currently assumes
without asking — the pull-request template and issue form under `.github/`,
the "Raise a question about this page" link in `overrides/main.html`, which
builds a GitHub `issues/new` URL, and `mkdocs.yml`'s `repo_url` and
`edit_uri`, which is what puts the edit pencil on every page. All four are
GitHub-shaped, all four are copied unconditionally today, and on a project
hosted anywhere else all four are dead weight shipped with instructions to
keep it. It also settles whether giscus is available at all, which
`docs/publishing.md` already documents as a public-repository feature.

## Available is not enabled

The workflows ship **as files in the scaffold**, and they ship **inert**.

A workflow described in prose and re-generated by whichever agent is running
is a fact generated at runtime, which
[`AGENTS.md`](https://github.com/roanboc/archreator/blob/main/AGENTS.md)
forbids in as many words; three adopters would get three workflows, none of
them reviewable in a diff and none checkable by CI. A workflow shipped at
`.github/workflows/` is worse in the other direction: the scaffold is copied
whole, so it would be live on the first push and red until somebody enabled
Pages — the failure that
[scope document 2](./2_publish-the-model-beyond-the-repository.md) declined to
ship.

So they live one directory away, at
`scaffold/.github/workflows-available/`, which is not a path the automation
host reads, and `establish-project` **moves** what the answer selects into
`.github/workflows/` and deletes the rest. It is the keep-or-delete pattern
that skill already applies to `open-questions.md` and `decisions/`, and it is
the constraint `RULE8` states.

## What this overturns, and what survives of it

Scope document 2 recorded, at the technology layer and under a granted gate:
*"`NODE3` — static hosting — is explicitly unchanged: nothing publishes these
models, and the method deliberately ships no workflow that would."* This
document contradicts that, and says so rather than quietly editing around it.

**The reasoning behind it survives intact.** Both stated objections were that
a workflow which fails until somebody enables Pages is worse than none, and
that Pages is wrong for a private model. Neither is answered by ignoring it;
both are answered by asking. The inert-until-activated rule is the first
objection, honored. The public-only branch is the second, honored — on the
free plan the private case is not a choice the method declines to make, it is
a thing the platform does not offer.

What was actually wrong in the old position is narrower than it looks: not
"the method should not publish", but "the method cannot know enough to
publish". It could not, because it never asked.

| Plateau | State |
| ------- | ----- |
| **Baseline** (before) | A method that renders a model and stops, and emits validators nobody runs. Where a project lives is never asked, so four GitHub-shaped assets are copied on faith and a publishing workflow lives as prose an adopter retypes |

## Work packages and deliverables

### WP1 — The scaffold carries the workflows, switched off

- **Deliverables:** `scaffold/.github/workflows-available/checks.yml`, running
  `check_links.py` and `check_model.py`;
  `scaffold/.github/workflows-available/publish-docs.yml`, building the portal
  with `build_docs.py` and deploying it to Pages; and a `README.md` in that
  folder naming what activates each and what has to be enabled first.
- **Outcome:** the workflow exists once, in a file that can be reviewed,
  diffed and linted, instead of in a fenced block in `docs/publishing.md` that
  every adopter retypes.

### WP2 — `establish-project` asks where the project lives

- **Deliverables:** the question and its activation table in
  `skills/establish-project/SKILL.md`; the keep-or-delete verdict extended to
  `.github/`, the `overrides/main.html` question link and `mkdocs.yml`'s
  `repo_url` and `edit_uri`; and the answer recorded in the project's own
  `architecture/5_technology/2_deployment.md`.
- **Outcome:** four host-shaped assets are kept or deleted on an answer rather
  than copied on faith, and the checks run on any GitHub project from its
  first push.

### WP3 — The public answer publishes, and opens the comment box

- **Deliverables:** activation of `publish-docs.yml` on the public answer, with
  the Pages setting it depends on stated where the Requester will read it; the
  giscus block in `mkdocs.yml` wired on the same answer and left alone
  otherwise; and the disclosure approval recorded in the adopting project's own
  scope document.
- **Outcome:** publishing a model publicly is a decision somebody made and
  signed, not a default that happened to be reachable.

### WP4 — The scaffold's deployment document finally exists

- **Deliverables:** `scaffold/architecture/5_technology/2_deployment.md`,
  already linked from `scaffold/architecture/README.md` and from
  `5_technology/README.md`, and until now resolving only because
  `check_links.py` exempts forward references.
- **Outcome:** the answer to WP2's question has a home that the layer's own
  numbering already reserved for it.

### WP5 — `docs/publishing.md` stops being the workflow's home

- **Deliverables:** the § Handing it to whoever will host it rewrite — the

## Gap notes

- **Azure DevOps, GitLab and everything else get nothing new.** Closing that
  is a second template folder per host and a wider answer, and it is cheap
  once the seam exists — which is most of what WP1 and WP2 are buying. What
  makes it not-now is that neither has a user waiting.
- **Private publishing stays unsolved, and stays honest.** The obvious fill is
  uploading `.docs/site/` and `architecture.pdf` as a workflow artifact or a
  release asset, which works on any repository at any plan. It is a genuinely
  useful third answer and it is deliberately not in this initiative, which is
  scoped to what the free plan can deliver.
- **This tree has no `5_technology/2_deployment.md`.** The method will require
  one of every project it bootstraps while its own model of itself does not
  carry one. Small, and better done as its own change than smuggled in here.
- **Nothing checks the shipped YAML.** A workflow file that no CI parses is a
  file that can rot. Adding `actionlint` to this repository's own checks is
  the fix, and it belongs to whichever initiative first regrets not having it.

## Open questions

- **Does Gate 3 get taken?** Recorded above as offered rather than assumed.
  The available-versus-enabled split and the folder name are cheap to change
  now and expensive once adopters have copied the scaffold, which is the
  argument for taking it.
- **Is `workflows-available/` the name?** `scaffold/workflows/` with a README
  does the same job and reads less like a borrowed convention. Either is inert;
  the choice is legibility, and it belongs to Gate 3 if Gate 3 is taken.
